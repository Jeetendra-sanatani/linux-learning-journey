## ⚡ Quick Theory — Public & Private Keys, Explained Simply

SSH key authentication uses TWO mathematically linked files:

```
Private key (id_ed25519)      → stays on YOUR machine, NEVER shared, ever
Public key  (id_ed25519.pub)  → safe to share, gets copied to servers you want to access
```

**The analogy that actually makes this click:** think of the public key as a padlock you hand out to anyone, and the private key as the ONLY key that opens it. You give servers the padlock (public key); only you have the matching key (private key) to prove it's really you.

**How login actually works (simplified):**
```
1. You try to connect to a server
2. Server has your PUBLIC key saved (in ~/.ssh/authorized_keys)
3. Server sends a challenge only your PRIVATE key can correctly respond to
4. Your private key answers → server trusts you → you're in, no password needed
```

**Generating a key pair — one command, two files created:**
```bash
ssh-keygen -t ed25519 -C "raven@example.com"
```
`-t ed25519` picks a modern, fast, secure key type (older setups use `rsa`, but `ed25519` is the current recommendation). `-C` just adds a label/comment, usually your email, to help you identify the key later.

🔑 **The golden rule:** your PRIVATE key file permissions matter A LOT — it should be `600` (owner read/write only). SSH will actually REFUSE to use a private key with overly open permissions, as a built-in security check.

## 💻 Let's Get Our Hands Dirty

*(Machine: Kali Linux | User: `raven`)*

### 🔑 Generating an SSH key pair
```bash
$ ssh-keygen -t ed25519 -C "raven@example.com"
Generating public/private ed25519 key pair.
Enter file in which to save the key (/home/raven/.ssh/id_ed25519): [Enter]
Enter passphrase (empty for no passphrase): [Enter or set one]

$ ls ~/.ssh
id_ed25519      id_ed25519.pub
```

### 🔍 Checking file permissions (important!)
```bash
$ ls -la ~/.ssh/id_ed25519
-rw-------  1 raven raven  411  id_ed25519      # 600 — correct, private key protected

$ chmod 600 ~/.ssh/id_ed25519      # fix it manually if it's ever wrong
```

### 📤 Copying your public key to a remote server
```bash
$ ssh-copy-id raven@192.168.1.100
raven@192.168.1.100's password: ********
Number of key(s) added: 1
```

### 🚀 Logging in — now WITHOUT a password
```bash
$ ssh raven@192.168.1.100
raven@remoteserver:~$          # logged in instantly, no password prompt!
```

### 🔧 Manual alternative (if ssh-copy-id isn't available)
```bash
$ cat ~/.ssh/id_ed25519.pub | ssh raven@192.168.1.100 "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"
$ ssh raven@192.168.1.100 "chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys"
```

### 📋 Viewing your public key content
```bash
$ cat ~/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAILx... raven@example.com
```

## 🐛 Gotchas That'll Trip You Up

- Accidentally copying your PRIVATE key instead of your public key to a server (or worse, sharing it) completely defeats the security model — treat your private key like a physical house key.
- Wrong permissions on `~/.ssh` (should be `700`) or `authorized_keys` (should be `600`) on the SERVER side can cause SSH to silently reject your key and fall back to asking for a password.
- Setting a passphrase on your key adds security but means you'll be prompted for it each time — use `ssh-agent` later to avoid re-entering it constantly (a topic for another day).

---

## 🧠 Today's Takeaway

Public key stays shareable, private key stays secret — that asymmetry is the entire foundation of SSH key authentication. `ssh-keygen` creates the pair, `ssh-copy-id` deploys your public key to a server, and from then on, logging in needs no password at all. This exact setup is standard practice on virtually every real production server.
